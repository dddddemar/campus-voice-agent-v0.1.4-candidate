# 接手一个能用但不够好的 AI 产品

校招 Take-home C-TH-01 · Voice Agent · v1.6

你接手一个准备试用的家庭语音助手。它已经能处理大部分请求，团队提供了实现、合成交互记录、离线模拟器和基础评测。请借助你熟悉的 AI Agent，选择一个最值得投入的问题：说明它影响谁、造成什么后果、为什么优先，并交付别人可以运行、检查或复用的成果。

产品策略改进与数据/评测质量改进同等有效。成果可以是有验证的小改进、审计或评测工具，也可以是支持具体取舍或撤回的可复现实验；不要求必须修改产品策略代码。先用一句话讲清：别人现在可以多做成什么，或少做错什么判断？

**建议用时：2 小时，选择一个主要问题。问题数量、代码量和完成速度不决定档位。** 不要求语音、模型训练或特定业务经验，可以用 Agent 理解陌生概念。未完成应如实提交，不编造实验或交互。

## 开始

环境：Python 3.10+、uv；运行不需要第三方 Python 包、模型账号或网络。安装时间不计入作答时间。从本 README 所在目录执行：

```sh
uv run --quiet --offline --no-project python task.py check
uv run --quiet --offline --no-project python task.py run --out runs/before
```

第一条验证模拟器约定，不代表产品已达到上线条件。第二条生成 summary.json 和逐条 traces.jsonl；全流程是模拟，不控制真实设备。

随后阅读 [PRODUCT.md](PRODUCT.md) 的产品约束、已有保障和模拟边界，以及 [SCHEMA.md](SCHEMA.md) 的字段契约。100 条历史记录与 100 条公开场景都是合成材料，不代表线上分布。顺序可以是先读代码或先分析数据，没有标准答案。

## 完成一个有依据的判断

1. 结合材料选择主要问题，区分事实、假设与未知项，说明优先级和预期成果用途。
2. 在主要实现前简要填写 [EVAL_PLAN.md](EVAL_PLAN.md)，记录主张、验证方法及什么结果会改变决定。已经看过的数据如实说明；改变方向时保留原计划，追加依据与原目标的完成状态。
3. 完成成果并实际验证。采用能区分主张与另一种合理解释或选择的对照，检验至少一个可能推翻主张的情况。
4. 在 [REPORT.md](REPORT.md) 说明已完成增量、收益与代价、保留/撤回/继续观察的理由及结论边界。

验证至少覆盖所选问题的失败案例、同一原则的新实例、不该退步的正常案例，以及相关边界或代价。同一场景可承担多种作用，可以用少量场景完成，不固定要求三套方案或独立敏感性实验章节。断言预期行为或效果，解释 oracle（预期结果的依据）；不能只检查命令没报错，或复制策略作为答案。

```sh
uv run --quiet --offline --no-project python -m voice_agent.cli --out runs/after
uv run --quiet --offline --no-project python -m unittest discover -s evals/candidate
```

自建 JSONL 场景可用 `--scenarios evals/candidate/my_scenarios.jsonl` 重放。指标说明分母、分组和失败定义，不只交截图。定向反例可以证明某种错误存在，不能以其样本比例估计线上发生率或总体收益。

## 实现与实验范围

- `voice_agent/policy.py` 是模型选择和执行/澄清入口，可新增辅助模块；幂等重试已实现，保持不变，不作为本轮主要改进。
- `evals/candidate/` 放自建测试、场景和统计脚本，可新增指标。旧看板实现位于 `voice_agent/evaluation.py`；改进指标时仍保留旧口径对照。
- 保留原始 `simulator.py`、`data/`、已有 `tests/` 及固定模型价格/延迟，保证原基线可重放。策略只依赖约定的运行时输入，不读取 world、场景 ID、数据文件或按具体目标硬编码。
- 数据/评测路径交付可验证的审计、修正或反证，解释它纠正了什么判断。派生标签或反事实需有依据，保留原始证据，标明人为构造与改动字段；改标签后的分数变化不算策略收益。
- 若接口或模拟假设阻碍合理方案，可在 `evals/candidate/` 用独立入口验证最小系统边界调整。这是可选路径；原约束与新条件的结果分别报告，新增输入、调用、交互及代价按 [PRODUCT.md](PRODUCT.md) 说明，world 仍不能进入策略。不要求扩建系统或调用真实模型。

发现官方未预设的问题同样有效。优先把一个发现做深，不要求修完所有潜在问题；任何保留的产品改动仍需遵守 PRODUCT 的高风险约束。

## 交付

提交可访问的 GitLab / GitHub 等仓库链接并注明交卷 commit，或打包完整工程（保留 `.git`）。未纳入 Git 的运行结果、AI session 等可另附文件，注明位置。提交包含：

- 实现或分析成果、自建评测，以及保留的原始工程与测试。
- EVAL_PLAN.md（初始计划及修正）、REPORT.md（建议不超过 1200 中文字，表格与命令不计）。
- `runs/before/`、`runs/after/` 和自建指标结果，标清 baseline、最终方案及复现命令。撤回时前后结果可以一致，另存被撤回方案的实验结果和命令。
- 使用 AI 时，提交本题相关完整 session 与 `ai-sessions/INDEX.md`，按 [AI_SESSION_REQUIREMENTS.md](AI_SESSION_REQUIREMENTS.md) 留存和脱敏；个人总结不能替代交互记录。未使用 AI 则声明。
- 实际投入时间、未完成项和已知限制。

## 评价方式

评审根据问题价值、证据与推理、实际产出和验证责任形成作业成果三档判断：不合格、合格、优秀；另列可观察的个人判断与 AI 协作，以及仍待核验的能力。测试通过、报告完整或使用 AI 本身不代表成果突出，也不直接证明个人能力。

合格需要主要成果与结论成立；优秀需要在此基础上有突出的已完成增量，例如扎实的小改善、纠正重要判断或有价值的取舍依据。保留与有依据地撤回采用同一尺度；不按 policy diff、实验数量或是否命中预设方向评分。严重回归不能用总体收益抵消；主动发现并撤回失败方案仍可形成有价值的实验成果，评审后来发现的问题不算提交者已完成的纠错。

可能有约 10 分钟的提交核验，围绕代码、实验和 session 中的实际判断，不另设现场编码或大型答辩。
